# 四个实际总权限（v2.11.0）

> v2.11.0 将用户授权统一为广告、链接、FBA 货件、紫鸟四个总开关。v2.10.0 的细分开关页与此前撤回的六类折叠方案属于历史行为，不应当作四总权限界面。安装新包不等于旧进程已加载新代码；升级后按下方步骤重启并核对，远端发布状态以对应 tag、安装包及校验值为准。

## 只管理四个开关

| 用户看到的总权限 | 开关 ID | 覆盖的现有精确操作 |
|---|---|---|
| 广告 | `ads.manage` | 23 项：SP 新建、改名、竞价策略／广告位、关键词／否词；SP／SB／SD 各自已支持的开停、竞价、投放与活动预算；SP 预算规则、投资组合，**以及 SP 账户总每日预算金额** |
| 链接 | `listing.manage` | 6 项：文案属性、主附图、A+、售价、优惠券／促销准备与网页交接、自发货（FBM）库存 |
| FBA 货件 | `fba.inbound` | 现有美国站先装箱入仓流程；计划、装箱、分仓、运输、窗口、跟踪及标签／提单 |
| 紫鸟 | `ziniao.control` | 现有紫鸟浏览器点击、填写等指定步骤 |

这是四个实际的统一授权入口，不是把原来的 31 个子开关折叠起来。设置页与原面板中的细分操作只用于说明权限范围，不再提供逐项授权控件。新数据目录默认全关；不存在“一键全开”。

精确提案中的 `op` 仍用原操作 ID，例如 `ads.sp.target.bid`、`ads.sp.account.budget`、`listing.attribute`。**不要把 `ads.manage` 或 `listing.manage` 填进提案当作操作 ID，也不要把细分操作 ID 当成公开开关 ID。** 原细分 ID 留作具体操作校验、既有状态兼容和审计，不等于仍有 31 个需要用户逐项点开的开关。

## 已有权限如何保留

读取、安装或升级不会自动改写原开关文件，也不会把缺失授权当成开启。只统计本组当前明确列出的操作，新能力不会仅凭 `ads.`／`listing.` 前缀自动获得权限。

- **全部已开**：总权限显示已开启。
- **全部已关或未授权**：显示已关闭。
- **旧细项有开有关**：显示“部分开启”（`partial: true`、`on: null`），既不是全部开启，也不是全部关闭。已有细项授权仍可能有效，不能把它误报为停权完成。
- 只有用户明确选择该总权限的“统一开启”或“统一关闭”，才统一写入本组成员；不会顺带改另三个总权限。保存期间发现旧状态已变更，应刷新核对，不能自动覆盖或重试。

开启「广告」会统一授权上述 23 项能力，包括账户总预算；开启「链接」会统一授权上述 6 项能力，包括售价和促销交接。操作前必须让用户看清完整范围，AI 不能为减少“部分开启”提示而擅自统一权限。

版本校验用于拒绝已检测到的陈旧状态；单次组保存采用一次原子替换以避免半写，**不提供 DSH、独立面板与 CLI 之间的跨进程锁或跨进程 CAS 事务**。不要同时在多个进程修改权限，也不能承诺所有竞态都会返回版本冲突；发现冲突后重新读取核对，不自动重发。

## 用户入口与旧命令

优先由用户在 `xander panel` 或支持的 DSH「设置 → Xander」操作。终端入口只接受以上四个公开开关 ID，例如以下命令**仅由用户本人运行**：

```sh
xander switch list
xander switch on ads.manage
xander switch off listing.manage
xander switch all-off
```

`all-off` 只用于用户主动紧急停权；没有 `all-on`。旧版针对细分操作 ID 的 `xander switch on/off <操作ID>` 不再是公开授权入口，不能自动把旧命令提升为整组授权。旧进程可能仍显示旧清单，完整管理须加载相匹配的新 Host 与页面；仅刷新页面不保证 Host 已更换。

AI 仍只能通过 `xander_switches` 只读查看，不得代拨开关、改文件、运行开关命令或调用面板写接口。

## 升级到 v2.11.0 后先重启并核对

1. **DSH：** 在当前 Desktop 的插件管理器更新 Xander 后，完整退出并重新启动 DSH，再重新打开「设置 → Xander」。不要手工切换 profile 或修改其包配置；仅刷新页面不能保证已加载的 Host 模块更新。
2. **Claude／Codex 等 MCP 宿主：** 停止并重启 Xander MCP 服务，必要时重启宿主应用，使工具、技能和业务模块从新包加载。不要把仓库或安装目录已更新当成旧 MCP 进程已经更换。
3. **原网页／终端：** 关闭旧面板标签页并停止原来的面板终端进程，确认终端使用新版 Xander 后重新运行 `xander panel`，使用新打印的完整本机网址。不要继续使用旧页面、旧口令或缓存的脚本。
4. **只读核对：** 用 `xander_status(check=false)` 核对运行版本，再用 `xander_switches({})` 核对四个总 ID、`23/6/1/1` 范围和旧权限的全部开／全部关／部分开启状态。此次核对不需要打开任何权限，也不执行亚马逊改动。

新版 DSH 和原面板只有在用户确认完整组范围后才提交 `permissionModel: 'masters-v1'`；新版 Host 拒绝缺失或错误标识的旧格式请求，防止旧细开关页面直接单击整组授权。旧页面不会自动转换成完整范围批准，应关闭后重新打开匹配的新页面。该标识是**兼容版本栅栏，不是身份凭证**，不宣称能防御同源脚本、浏览器自动化或同机任意代码。

版本号、四卡截图或历史验收记录不能替代新进程与新页面的实际核对；升级也不会自动统一旧授权。完成只读核对后，是否统一某个总权限仍由用户本人决定。

## 合并权限不合并执行批准

四个开关只决定允许申请哪些能力，**不是批准任意账户改动**。每次写入仍走：

`xander_prepare_change` → 完整展示该份精确新旧值表 → 用户明确批准 → `xander_execute_change` 一次 → 独立回读／必要时 `xander_verify_change`。

以下业务边界不变：

- SP 账户总预算的操作 ID 仍为 `ads.sp.account.budget`，仅修改 US／NA seller SP 的正数 `dailyBudget`，不切换控制台预算模式，不代表取消总上限，也不修改活动预算、竞价或 SB／SD。读到该数字不等于知道生效模式；未知结果只核验、不重发。
- 新建广告活动、广告组、广告商品默认暂停；启用须另行批准相应具体操作。
- 图片贡献回读不等于零售页已换图；A+ 草稿、关联、审核、批准与发布分别核验。
- 优惠券／促销仍只有准备、网页交接和官方只读查询，交接就绪不等于已提交，不因归入「链接」获得新的 API 写能力。
- FBA 每份提案一个动作；分仓费、运输报价与合作承运扣款分别明确批准，异步受理不等于完成，标签生成不等于发运。
- 紫鸟仍需对准确的浏览器、亚马逊后台网址与具体点击／填写步骤批准，不能借「广告」或「链接」绕过「紫鸟」权限。

验证范围见[DSH 验收记录](<dsh-settings-verification.md>)中的发布前复核与历史条目；历史测试、旧版截图或本页说明不等于当前发行已在真实 GUI 冷加载、执行权限写入或完成远端发布。
